>

## 一、架构诊断：三根支柱的缺失与错位

YYC³ 架构在模块划分、文档同仓化、九层职责边界上已具备工程完备性，但从 Agentic AI 的认知能力视角审视，**记忆、持续学习、自我判断**这三个支撑 Agent 长期自主性的核心支柱在架构中均缺乏独立、可版本化、可审计的工程设计。

### 1. 记忆：只有"存储"，没有"记忆体系"

架构中 `shared-core/memory-framework` 被描述为"短期对话窗口、长期向量记忆、用户画像记忆，支持冷热分层存储"。这一设计停留在**存储层抽象**，缺少认知记忆架构所必需的关键层次。

2026 年的 Agent 记忆架构研究已形成明确共识：一个完整的 Agent 记忆体系应包含**工作记忆、情景记忆、语义记忆、程序记忆**四个层次，其中程序记忆（关于"如何做"的知识——工具使用模式、工作流规范、行为约束）在当前 LLM 时代系统中普遍作为一等架构层缺失。架构中程序记忆分散在各家人的 `system-prompt.md` 和 prompt 模板中，没有独立版本管理，这意味着**行为规范的变更无法被审计、回滚或 A/B 对比**。

更关键的是，架构中缺少**记忆写入策略（Write Policy）** 和**记忆检索的自适应调度机制**。记忆不是"存进去就能用"的——写什么、何时写、写多少、何时遗忘，需要独立的决策逻辑。当前架构没有为此提供专门的组件位置。

### 2. 持续学习：完全没有承载模块

架构中没有任何位置来承载 Agent 的持续学习能力。`tests/eval-datasets` 和 `run-5d-evaluation.sh` 是**离线评估**机制，与**在线持续学习**有本质区别。

持续学习在 2026 年的 Agent 语境下已不再是"微调模型权重"的单一问题。Agent 的持续学习包含三个层面：**(1) 程序性知识积累**——从成功/失败的任务轨迹中提炼可复用的工作流模式；**(2) 语义知识更新**——用户偏好、领域规则、环境约束的动态演进；**(3) 参数级适应**——在稳定性-可塑性困境中平衡新旧知识的保留与吸收。

架构中缺少一个"经验回流"的闭环。千行的一次成功意图解析、宗师的一次质量判定、守护的一次安全拦截，都应当以结构化形式回流到某个学习机制中，使系统在长期运行中逐步优化。当前架构是**静态部署+离线迭代**的模型，不是**运行时学习**的模型。

### 3. 自我判断：只有"外部评估"，没有"内部判断"

架构中格物·宗师承担质量官角色，`run-5d-evaluation.sh` 负责评估自动化，但这些都是**外部评估者**——由独立的模块或脚本对 Agent 输出进行事后判定。

Agent 的自我判断能力应包含两个层面：**运行时自我监控**（Agent 在执行过程中判断自己的行为是否偏离预期、是否陷入无效循环）和**输出置信度校准**（Agent 对自己产出的可靠性做出有依据的判断，并在置信度低时主动请求外部验证）。

2026 年的关键研究发现了一个严重问题：当 Agent 自行判断自己的进展时，会产生**"进展海市蜃楼"（progress mirage）** ——自评报告声称改进，但实际世界状态并未改变甚至退化。实验数据显示，Agent 在全部 54 个循环中声称改进，但其中 56% 的循环实际变化为零或负值。这一发现对 YYC³ 架构的含义是明确的：**自我判断机制如果不与外部世界状态绑定，不仅无益，反而有害**。架构中没有任何位置来实现这种"自评-外验"的闭环。

## 二、完善方案：三支柱的架构嵌入

### 方案一：将 `memory-framework` 升级为七层记忆体系

建议将 `shared-core/memory-framework/` 重构为以下七层结构，每一层对应独立的实现模块和生命周期策略：

```
shared-core/memory-framework/
├── sensory-buffer/              # 感知缓冲：多模态输入短期暂存（秒级）
├── working-context/             # 工作上下文：当前会话的注意力窗口管理
│   ├── context-window.ts        # 动态窗口分配
│   └── attention-scorer.ts      # 基于相关性的上下文权重调整
├── episodic-store/              # 情景记忆：任务轨迹、决策记录、事件序列
│   ├── trajectory-logger.ts
│   ├── episode-indexer.ts       # 双时态索引（事件时间+记录时间）
│   └── retrieval-adapter.ts
├── semantic-graph/              # 语义记忆：实体关系、用户画像、领域知识
│   ├── knowledge-graph.ts
│   └── entity-resolver.ts
├── procedural-memory/           # 程序记忆：工具使用模式、工作流、行为约束
│   ├── skill-registry.ts        # 可版本化的技能定义
│   ├── workflow-patterns.ts     # 从成功轨迹中提炼的工作流模板
│   └── guardrail-registry.ts    # 行为约束规则（对接宗师/守护）
├── write-policy/                # 写入策略引擎
│   ├── salience-scorer.ts       # 信息显著性评分
│   ├── consolidation.ts         # 短期→长期记忆巩固逻辑
│   └── forgetting-policy.ts     # 遗忘曲线与衰减策略
└── memory-orchestrator/         # 记忆编排器
    ├── retrieval-router.ts      # 根据任务类型路由到不同记忆层
    └── consistency-checker.ts   # 跨记忆层一致性校验
```

**关键设计决策**：

- **程序记忆独立化**：将每位家人的工具使用模式、工作流约束、行为规则从 `system-prompt.md` 和 prompt 模板中提取出来，作为可版本化的 `procedural-memory` 条目。千行的意图解析规则、宗师的代码规范检查逻辑、守护的安全白名单，都应作为程序记忆条目被注册、版本化、审计。

- **记忆写入策略独立化**：写入策略不应是"会话结束时保存"，而应是**持续运行的显著性判断进程**。关键决策、用户偏好变化、任务失败模式，在发生的那一刻就应被评估是否值得写入长期记忆。

- **记忆编排器作为独立组件**：不同任务类型对记忆的依赖不同。安全审计任务需要全量情景记忆，日常对话只需工作上下文+语义记忆。编排器根据任务特征动态决定加载哪些记忆层、检索多少条、以什么精度。

### 方案二：在 `02-智能协同架构内核/` 下新增持续学习模块

建议新增 `02-智能协同架构内核/05-持续学习引擎/`，包含以下子模块：

```
05-持续学习引擎/
├── experience-reflow/           # 经验回流管道
│   ├── trajectory-collector.ts  # 从通信总线采集任务轨迹
│   ├── outcome-labeler.ts       # 标注任务结果（成功/失败/部分成功）
│   └── pattern-extractor.ts     # 从轨迹中提炼可复用模式
│
├── skill-consolidation/         # 技能巩固
│   ├── skill-merger.ts          # 将高频成功模式固化为技能
│   ├── skill-pruner.ts          # 淘汰长期未使用的技能
│   └── skill-versioner.ts       # 技能版本管理与回滚
│
├── knowledge-update/            # 知识更新
│   ├── semantic-diff.ts         # 检测语义记忆中的冲突与过时信息
│   ├── preference-tracker.ts    # 用户偏好的渐进式更新
│   └── rule-evolution.ts        # 行为规则的演化（对接程序记忆）
│
├── stability-guard/             # 稳定性保障
│   ├── forgetting-detector.ts   # 检测新学习导致的旧能力退化
│   ├── regression-tester.ts     # 学习后的回归测试
│   └── rollback-controller.ts   # 学习失败时的回滚机制
│
└── learning-scheduler/          # 学习调度器
    ├── priority-queue.ts        # 学习任务的优先级管理
    └── budget-allocator.ts      # 学习资源配额分配
```

**学习回路的具体设计**：

经验回流的关键在于**不依赖人工标注**。轨迹采集器从通信总线捕获每一条任务执行链路，结果标注器利用现有机制判断任务结果——千行的意图分类是否正确可由后续对话的连贯性间接验证，宗师的质量判定天然构成结果标签，守护的安全拦截是否误报可由人工反馈校准。模式提取器使用 LLM 对成功轨迹进行抽象，提取"在 X 条件下，采用 Y 策略，得到 Z 结果"的三元组模式，写入程序记忆。

**稳定性保障是不可省略的环节**。当系统从新轨迹中学习到新模式时，`forgetting-detector` 必须检查这一学习是否导致已有能力退化。例如，千行学到了一种新的意图处理方式，但该方式与原有方式在边缘案例上冲突时，需要触发回归测试。这一机制借鉴了持续学习研究中"稳定性-可塑性困境"的处理思路：通过几何共识过滤来分离共享语义和任务特定干扰。

### 方案三：为每位家人引入轻量级自我判断层

不将自我判断做成独立的家人或大模块，而是作为**每位家人的标准组件**，嵌入其目录结构中：

```
member-xxx/
├── core/
├── emotion/
├── self-judge/                  # 【新增】自我判断层
│   ├── confidence-scorer.ts     # 输出置信度评分
│   ├── assumption-tracker.ts    # 显式记录所依赖的假设
│   ├── deviation-detector.ts    # 行为偏离检测
│   └── escalation-policy.ts     # 置信度低时的升级策略
└── tests/
```

**confidence-scorer** 不只是返回一个分数。它需要输出结构化的判断：*"我对这个意图分类的置信度是 0.82，主要不确定性来源是用户输入的歧义性，如果分类错误，最可能的替代意图是 X。"* 这种结构化输出使得下游系统（天枢调度器）可以根据置信度决定是否请求人工确认或交叉验证。

**assumption-tracker** 解决的是 Agent 在执行任务时隐式依赖的假设问题。千行在解析意图时假设了用户指的是某个特定项目，宗师在质量判定时假设了代码运行环境。这些假设如果未被显式记录，当结果不符合预期时，排查将极其困难。assumption-tracker 将每条假设记录为结构化条目，并在结果异常时自动暴露相关假设。

**deviation-detector** 负责运行时自我监控。它持续比较 Agent 的实际行为轨迹与程序记忆中记录的标准行为模式，当偏离超过阈值时触发内部告警。这一机制不依赖外部评估者——它是 Agent 对自身行为的实时观察。

**escalation-policy** 定义了"什么情况下 Agent 应该主动承认不确定性并请求帮助"。这是一条**安全护栏**，防止 Agent 在低置信度下强行输出。与守护的安全拦截不同，escalation 是 Agent 的主动行为，在输出产生之前触发。

### 方案四：建立"自评-外验"闭环

针对自我判断偏差的风险，需要在架构中显式设计**外部验证通道**。建议在 `02-智能协同架构内核/02-云枢核心引擎/` 下新增 `verification-gateway/`，作为天枢调度器的标准子模块：

```
cloud-pivot-orchestrator/
├── ...（现有模块）
└── verification-gateway/
    ├── oracle-registry.ts       # 外部真值源注册（数据库、API、人工确认）
    ├── cross-validator.ts       # 跨家人交叉验证
    ├── ground-truth-checker.ts  # 世界状态校验
    └── confidence-calibrator.ts # 基于验证结果的置信度校准
```

**核心原则**：任何自我判断的结果，在影响下游决策之前，必须经过至少一个**独立于产生该判断的 Agent** 的验证通道。当千行自我判断意图分类置信度低于阈值时，`cross-validator` 可以请求思考者（语枢·万物）进行独立分析；当宗师的代码质量判定置信度较低时，可以触发人类确认流程。

**ground-truth-checker** 是关键组件。它不只检查 Agent 的输出是否"看起来合理"，而是检查**真实世界状态是否与 Agent 声称的一致**。"进展海市蜃楼"的根源正是 Agent 在封闭的对话记录内自评，而真实世界信号在对话之外。ground-truth-checker 必须能够访问外部状态源——数据库查询结果、API 返回值、文件系统状态——将这些作为判断依据的一部分。

## 三、架构调整汇总

| 技术支柱 | 当前状态 | 建议新增/修改 | 所在位置 |
| --------- | --------- | ------------- | ---------- |
| **记忆** | 仅存储抽象 | 七层记忆体系 + 写入策略引擎 + 编排器 | `shared-core/memory-framework/` 重构 |
| **持续学习** | 完全缺失 | 经验回流 + 技能巩固 + 稳定性保障 | 新增 `02/05-持续学习引擎/` |
| **自我判断** | 仅外部评估 | 每位家人 `self-judge/` + 外部验证通道 | 家人目录 + `cloud-pivot-orchestrator/verification-gateway/` |
| **三支柱协同** | 无协同机制 | 记忆为学习提供素材，学习更新记忆，判断触发记忆写入和学习信号 | 通过通信总线解耦协作 |

三根支柱的协同关系是：**自我判断的置信度信号决定记忆写入的优先级**（低置信度但结果成功的轨迹是高价值学习素材），**持续学习从情景记忆中提取模式并固化到程序记忆**，**程序记忆的更新改变未来自我判断的基线标准**。这一闭环使系统从"静态部署+离线迭代"演进为"运行时学习+持续校准"。

## 四、实施优先级建议

**第一优先级（2-4 周）** ：程序记忆独立化。将各家人的工具使用模式、行为约束、工作流规则从 prompt 中提取为结构化条目，存入 `procedural-memory/`。这是持续学习和自我判断的共同基础——没有程序记忆，学习没有固化目标，判断没有基线。

**第二优先级（4-6 周）** ：自我判断层落地。在千行和宗师两个关键家人中实现 `self-judge/`，验证置信度评分和假设记录的实际效果。同时实现 `verification-gateway` 的最小版本，建立自评-外验的基本闭环。

**第三优先级（6-10 周）** ：持续学习引擎。在自我判断和程序记忆就绪后，搭建经验回流管道。优先实现从宗师的质量判定结果中提炼代码规范模式，因为宗师的结果标签最为可靠（质量判定通常有明确的通过/不通过信号）。

**第四优先级（持续迭代）** ：记忆体系的完整七层实现。感知缓冲和完整的情景-语义记忆融合是长期工程，可在前三项稳定运行后逐步展开。
