## 〇、结论摘要

**一句话**：本仓已经完成「**契约层**」（清单 / 卡片 / 提示词 / 指标），但「**能力层**」尚未打通——45 条技能是描述性条目、MCP 只有传输没有协议语义、插件体系零代码。2026 年生态正好收敛为 **Skill / MCP / Plugin** 三层能力分发标准，与本仓既有资产高度同构，**无需推翻重做，只需把契约层向下生成、向上注册**。

四项判断：

| # | 判断 | 依据 |
| - | ---- | ---- |
| 1 | **技能真正的问题不是「缺实现」，而是「三套表示互不相通」** | manifest 45 条（`shared.*` / `{slug}.*`）、`SkillRegistry.SkillDefinition`（含 steps）、学习引擎 `FileSkillStore`（`skill-xxxxxxxx` FNV 自造 id）三者无 id 映射、无加载器 |
| 2 | **MCP 的差距是「协议语义」，不是「传输」** | [types.ts](file:///Users/yanyu/YANYUCLOUDCUBE/YanYuCloudCube/YYC3-AI-FAmily-Agent/architecture-kernel/02-云枢核心引擎/mcp-adapter/types.ts#L5) 自述「只做编解码与进程传输，不实现工具语义（tools/list 等）」；`StdioMcpTransport.request()` 已具备客户端能力却无人调用 |
| 3 | **插件不是从零开始，`LayerCapability` 与 EventBus 已是两个注册点** | 20 个契约骨架文件统一 `id / describe() / health()` 三元接口；全库零 plugin 代码，但扩展范式已存在 |
| 4 | **已有两个「生成式强契约」范式可直接复制到技能** | Agent Card 由 manifest 生成（`gen-agent-cards.mjs`）+ 零漂移校验；提示词 `PROMPT_META` 双向版本校验——技能缺的正是这一对 |

**演进主线**：`P2 生态外挂（已规划，落地补齐）` → `P3 技能可执行化（本档新增）` → `P4 插件化与能力注册中心（本档新增）`，三阶段全部遵守零运行时依赖、hermetic 门禁、单进程模型三条红线。

| 服务端语义 | ⚫ 零 | `tools/list` / `tools/call` / `resources` / `prompts` / `initialize` 均无 |

> 关键判断：**现状是「把总线事件伪装成 JSON-RPC」，不是 MCP 实现。** 但底层分帧、请求关联、超时、错误码这些最难写的部分已经就绪——补语义比补传输便宜一个数量级。

### 1.4 插件：只有扩展点，没有扩展体系

- 代码中 `plugin|插件|extension|addon` **零匹配**（仅文档叙述）
- 最接近的骨架：`LayerCapability { id, describe(), health() }`（20 个契约文件，每层一个薄实现 + `TODO(infra)`）
- 两个真实注册点：`EventBus.subscribe`、`EventBus.registerMcpAdapter`
- 文档设想（九层架构 §插件系统）：插件管理器 / 市场 / 开发 SDK / 生命周期 / 权限管理 —— 全部为目录树，无设计细节

**结论**：插件化应当**从「能力注册」而非「代码加载」切入**——先让技能与 MCP 工具可被枚举、寻址、授权、审计，再谈动态装载。这样既符合零依赖约束，也避免引入 `vm` / 动态 `import()` 带来的安全与 hermetic 风险。

## 二、生态调研（2026 现状）

### 2.1 三层能力分发模型已成事实标准

2026 年社区形成清晰分层，三者互补而非竞争：

| 层 | 回答的问题 | 载体 | 发现方式 |
| -- | ---------- | ---- | -------- |
| **Skill** | 「**怎么做**」——程序性知识 / 工作流 / 判断准则 | `SKILL.md` + `references/` + 可选脚本 | 目录扫描 / 注册中心（按需加载） |
| **MCP Server** | 「**能调什么**」——外部工具与资源 | JSON-RPC server（stdio / HTTP） | `tools/list` / 注册中心 allowlist |
| **Plugin** | 「**如何打包分发**」——把 skill + MCP + 元数据打成可安装单元 | 插件包（plugin manifest + 内容） | 插件市场 / catalog 多 scope 解析 |

**对本仓的直接含义**：`shared.mcp-tool` 与 `shared.a2a-delegate` 是「能力」，32 条专用技能是「知识」，二者都不该混在同一个抽象里。P3 必须先分层建模。

### 2.2 MCP 2026-07-28：历史上最大一次修订

官方博客明确该版本为「自发布以来最大的协议修订」，核心变化：

- **无状态协议核心**（stateless core）——降低部署与水平扩展门槛
- **多轮往返请求**（Multi Round-Trip Requests）——服务端可中途向客户端索取输入
- **基于 header 的路由**——网关/多租户场景必需
- **可缓存的列表结果**——`tools/list` 等可被缓存，降低轮询成本
- **授权加固**——OAuth 资源指示器等安全要求收紧
- **正式扩展框架（extensions framework）**——官方承认「核心 + 扩展」的分层演进
- **Tier 1 SDK 更新**；**含破坏性变更**，需按发布时序迁移

**迁移判断**：本仓当前**没有实现任何标准语义**，因此「破坏性变更」对我们**零成本**——反而可以从第一天就对齐新规范，跳过旧版兼容包袱。这是难得的后发优势。

### 2.3 Agent Skills：从私有格式到开放规范

- Anthropic 于 2025-10 提出，现已为**开放规范**，被约 **40 个产品**读取
- 核心是 `SKILL.md`（frontmatter + 正文）按需加载程序性知识，配套 `references/` 渐进披露
- `agentskills.io` 倡议正在标准化三个层面：**文件格式层 / 能力发现层 / 执行语义层**
- 学术界已给出工程化准则：技能是**软件制品**，应遵循单一职责、接口与实现分离、低耦合、**共享 token 预算下的经济性**，并用**行为评测**替代确定性断言
- 出现包管理器与注册中心尝试（如 Skilldex：层次化 scope、metadata-only registry）

**对本仓的直接含义**：本仓 `.skill` ZIP 已是标准形态；缺的是**由 manifest 生成**、**纳入门禁校验**、**统一 id**、**渐进披露**（元数据先行，正文按需）。

### 2.4 A2A 1.0：跨框架协作的事实标准

- 2025-04 由 Google 发起，现由 **Linux Foundation** 治理；2026-04 宣布 **150+ 组织**采用，深度集成 Google / Microsoft / AWS 平台
- 2026-08 并入 **Agentic AI Foundation**
- 规范 v1.0.0 核心：**Agent Card**（`/.well-known/agent-card.json`，描述身份 / 能力 / 技能 / 端点 / 认证）+ 任务委托（同步、SSE 流式、异步推送）+ 富数据交换
- 价值主张：跨框架交接工作不再需要为每一对 Agent 写定制集成

**对本仓的直接含义**：本仓 **8 张 Agent Card 已与 A2A 语义对齐**（`name/description/url/version/provider/capabilities/skills/authentication/security/slo`），只差**发布端点**与**委托实现**——这正是既有 P2-T2 的范围。

### 2.5 Plugin 1.0 与注册中心治理

- **Agent Plugins 1.0**：多厂商开放标准，目标是「可移植的 AI 技能 + MCP」；CLI 侧已出现 **多 scope catalog 解析**（local / user / org / marketplace，按优先级覆盖）
- **企业级 MCP Registry**：不止「列出工具」，而是**集中治理**——认证、鉴权、审计日志、策略执行、allowlist、版本钉扎、RBAC、审批门
- 平台侧实践（GitHub / Kong 等）：注册中心 + **allowlist 准入** + 安全扫描 + 合规，形成「只允许安装已批准清单」的治理闭环
- 社区共识预测：2026 年内**层内收敛**（SKILL.md 成为各宿主标配、MCP 官方 Registry 落地、插件市场收敛为少数几家），层间不会合并

**对本仓的直接含义**：注册中心应当**先做「静态清单 + 校验脚本 + 审计」**（完全零依赖、可入 Git、可被门禁验证），**不要**先做动态安装器。

## 三、目标架构

### 3.1 能力供给三层（本仓版）

```
┌─────────────────────────────────────────────────────────────┐
│ L3 分发层 · Plugin / Capability Pack                        │
│    plugin.yaml（id/version/scope/contents/allowlist/hash）   │
│    = skills/*  +  mcp-servers/*  +  policies/*  +  prompts/* │
├─────────────────────────────────────────────────────────────┤
│ L2 执行层 · Capability Runtime                              │
│    技能运行时：SkillDefinition（统一 id，含 steps）           │
│    工具运行时：McpToolDescriptor（tools/list 可见）           │
│    二者共用：PolicyRegistry 授权 + ComplianceAudit 留痕       │
├─────────────────────────────────────────────────────────────┤
│ L1 契约层 · Manifest（唯一事实源，已有）                      │
│    family-manifest.yaml：8 家人 × 45 技能 × 16 提示词         │
│    → gen-agent-cards      （已有，A2A）                      │
│    → gen-skill-artifacts  （新增，Agent Skills）             │
│    → mcp tool catalog     （新增，MCP）                      │
└─────────────────────────────────────────────────────────────┘
```

**核心原则**：**单向生成**（manifest → 产物 → 运行时），禁止反向手写；产物一律可 `--check` 零漂移。

### 3.2 统一 id 与命名空间

一条 id 贯穿三层，彻底消除三体分裂：

| 层 | id 形态 | 示例 |
| -- | ------- | ---- |
| manifest 技能 | `{owner-slug}.{skill-slug}` | `qianhang.intent-detection` |
| SKILL.md 目录 | `skills/{owner-slug}/{skill-slug}/SKILL.md` | `skills/qianhang/intent-detection/SKILL.md` |
| 运行时注册 | 同 manifest id（`SkillRegistry.register` 校验前缀归属） | `qianhang.intent-detection@1.0.0` |
| MCP 工具名 | `{owner-slug}__{skill-slug}`（MCP 要求 `[a-zA-Z0-9_-]`，故 `.` → `__`） | `qianhang__intent_detection` |
| 学习引擎沉淀 | 复用同一命名空间，禁止 `skill-xxxxxxxx` 自由 id | `learned.qianhang.intent-detection.v2` |

**兼容策略**：`FileSkillStore` 的 FNV id 保留为**内部主键**（不破坏已落盘数据），但新增 `logicalId` 字段映射到统一命名空间；读取时按 `logicalId` 归并。这是一次性迁移，不做双写。

### 3.4 五维对齐

| 五维/五高 | 落点 |
| --------- | ---- |
| **高可用** | MCP 无状态核心 + 请求超时 + DLQ 兜底；技能加载失败降级到规则主选 |
| **高性能** | 渐进披露（元数据索引先行，正文按需加载）；`tools/list` 结果可缓存 |
| **高安全** | 工具调用过 `PolicyRegistry`（默认 observe）；注册中心 allowlist；包完整性哈希 |
| **高扩展** | 三层模型 + scope catalog；新增技能只需改 manifest |
| **高智能** | 学习引擎沉淀技能回流 manifest（`status: planned` → `active` 的晋升通道） |
| **标准化/规范化** | 一个 id、一个事实源、一次生成、一次校验 |
| **自动化** | `gen-skill-artifacts --check` 入 CI；`manifest:check` 扩展技能段 |
| **可视化** | 面板新增「能力供给」卡片（技能 45 / 工具 N / 插件 M） |

## 四、演进路线

> 排期原则：**先打通契约（P3 前半），再做协议（P3 后半），最后做分发（P4）**。P2 为既有规划，本档只做落地补充，不重复定义。

### 4.1 P2 · 生态外挂（v3.0，既有规划，补齐执行细节）

| 编号 | 任务 | 交付物 | 验收 |
| ---- | ---- | ------ | ---- |
| P2-T1 | 外部 worker 契约 | `presets/external-worker/worker.yaml.tpl`（`endpoint/capabilities/auth/timeout/fallback/capabilitiesRef`） | capability id 与 manifest 对齐，不得自造 |
| P2-T2 | A2A 适配层 | `architecture-kernel/a2a-adapter/`：card 发现 + 任务委托 + 结果归一 | ≥3 例（成功/超时/非法响应入 DLQ）；**纯内存 stub，零网络** |
| P2-T3 | 外部门控 runner | `scripts/run-external-uats.mjs`，三闸门控 | 与 `uat:llm` 同构；默认不进 SPECS；跳过仍记 0 |
| P2-T4 | 安全策略映射 | 零信任/内容过滤/注入检测 → `PolicyRegistry` YAML | 默认 observe；enforce 需显式开关 |
| P2-T5 | 编排边界 | `docker/` 独立 compose（端口避开 3030） | 不参与 regression，不进根 scripts 必选链 |

**本轮补充建议**：P2-T2 的 Agent Card 发现应**直接复用现有 8 张卡**（已在 `assets/agent-cards/`，schema 对齐 A2A），无需新建格式——只需补一个 `/.well-known/agent-card.json` 的路径映射函数。

### 4.2 P3 · 技能可执行化（v3.1，本档新增）

**目标**：让 45 条技能从「描述」变成「可发现、可加载、可执行、可评测」的资产，且**不引入任何运行时依赖**。

| 编号 | 任务 | 交付物 | 验收标准 | 门禁影响 |
| ---- | ---- | ------ | -------- | -------- |
| **P3-T1** | 技能契约补全 | manifest `skills[]` 增 `version` / `steps[]` / `io` / `status`；`family-manifest.mjs` 增校验 | 45 条全部有 `version`（语义化）；`dedicated` 必须 ≥1 step；`kernel` 锚点校验升级为「导出符号存在」 | 0 新增依赖；`manifest:check` 通过 |
| **P3-T2** | 技能产物生成 | `scripts/gen-skill-artifacts.mjs` → `skills/{owner}/{skill}/SKILL.md`（frontmatter: `name/description/version/owner/allowed-tools`）+ `references/` | 45 个目录生成；`--check` 零漂移；孤儿目录扫描 | 新增 1 个契约套件（≥6 例） |
| **P3-T3** | 统一 id 与加载器 | `skill-registry.ts` 增 `logicalId` + `loadFromManifest()`；`FileSkillStore` 增 `logicalId` 映射 | 三套体系 id 可互查；`skill-xxxxxxxx` 可归并到 `learned.*` | 新增 ≥4 例 |
| **P3-T4** | 渐进披露检索 | 元数据索引（id + 一句描述 + tags，≤200 token）与正文分离；`SkillRegistry.match(query)` 先查索引 | 索引加载不读正文；命中后才加载 `steps` | 新增 ≥3 例 |
| **P3-T5** | 行为评测 | `tests/skills/` 金样例：给定输入，断言「调用了哪些 step / 产出结构合法」 | 每条 `status: active` 技能至少 1 例；评测失败不阻断（先 observe） | 新增套件，初始 observe |
| **P3-T6** | 面板能力供给卡片 | `data.json` 增 `capabilities: {skills, tools, plugins}` | 面板显示 45 / N / M | 面板测试更新 |

**入口判据（DoD）**：`pnpm regression` 仍全绿；`tsc --noEmit` 干净；新增套件全部计入五支柱（学/治为主）。

### 4.3 P4 · 插件化与能力注册中心（v3.2，本档新增）

**目标**：把「技能 + MCP 工具 + 策略 + 提示词」打成可分发的**能力包**，并建立**可审计的准入治理**。

| 编号 | 任务 | 交付物 | 验收标准 |
| ---- | ---- | ------ | -------- |
| **P4-T1** | 能力包格式 | `plugins/{id}/plugin.yaml`（`id/version/scope/contents[]/integrity/targets`） | schema 校验；`contents` 只能是 `skills/mcp-servers/policies/prompts` 四类 |
| **P4-T2** | 静态注册中心 | `architecture-kernel/10-能力注册中心/catalog.ts`：加载 → 解析 scope（`builtin` / `local`）→ 合并 | 多 scope 覆盖顺序确定且可测；零网络 |
| **P4-T3** | 准入治理 | `allowlist.ts`：默认 **observe**（只记审计），`enforce` 需显式开关 | 未准入包被调用时写 `ComplianceAudit`；enforce 下拒绝并计数 |
| **P4-T4** | 完整性校验 | 包内容哈希（`node:crypto` SHA-256）+ 清单声明比对 | 篡改即校验失败并告警 |
| **P4-T5** | MCP 工具目录 | manifest 技能 → `tools/list` 结果；`tools/call` 经 Policy 后分派 | 工具名符合 MCP 命名；未准入工具不可见 |
| **P4-T6** | 打包/检查 CLI | `scripts/pack-plugin.mjs`（`--check` 模式） | 生成物可入 Git；CI 零漂移 |

**边界（明确不做）**：不实现动态 `import()` 装载任意代码；不实现远程安装/下载；不引入 `vm` 沙箱；不做插件市场服务端。**插件 = 静态可校验清单 + 已编译模块的注册**，不是运行时加载器。

### 4.4 阶段依赖与里程碑

```
M8 (P2-T1/T3) ──┐
M9 (P2-T2/T4/T5)─┴─→ M10 (P3-T1/T2 契约与产物) ─→ M11 (P3-T3/T4/T5 运行时与评测)
                                                      └─→ M12 (P4-T1/T2/T4 注册中心)
                                                             └─→ M13 (P4-T3/T5/T6 治理与工具目录)
```

| 里程碑 | 判据 |
| ------ | ---- |
| M10 | `skills/` 45 目录生成且 `--check` 零漂移 |
| M11 | 三套技能 id 可互查；索引加载不读正文；行为评测可跑 |
| M12 | 能力包可打包、可校验、可由 catalog 解析 |
| M13 | 未准入工具在 observe 下留痕、enforce 下拒绝；`tools/list` 与 manifest 一致 |

## 五、关键设计决策（ADR）

| # | 决策 | 选项 | 结论与理由 |
| - | ---- | ---- | ---------- |
| **D1** | 零依赖下如何实现 MCP server | ① 引官方 SDK ② 手写 JSON-RPC 子集 | **②手写**。核心方法仅 6 个，`StdioMcpTransport` 已解决分帧与请求关联；引 SDK 破坏零依赖红线 |
| **D2** | 技能 id 如何统一 | ① 全量重命名 ② 双轨并存 ③ 新增 `logicalId` 映射 | **③**。已落盘 `skill-xxxxxxxx` 数据不动，新增逻辑层映射，一次性迁移 |
| **D3** | `SKILL.md` 手写还是生成 | ① 手写（标准形态）② manifest 生成 | **②生成**。手写必然漂移；生成 + `--check` 才有契约强度；与 Agent Card 同构 |
| **D4** | 注册中心放哪 | ① 独立服务 ② 静态 JSON + 脚本 ③ 数据库 | **②**。可入 Git、可被门禁验证、零依赖；未来需要动态时再加薄 HTTP 层 |
| **D5** | 门禁如何隔离外部能力 | ① 全部纳入 ② 全部排除 ③ 契约纳入、运行时排除 | **③**。契约（清单/产物/包格式）入 hermetic 门禁；外部端点走三闸门控、默认跳过 |
| **D6** | 技能评测用断言还是行为 | ① 确定性单测 ② 行为评测 | **混合**：结构断言确定性；语义质量用金样例行为评测，先 observe 后 enforce（对齐 arXiv 观点） |

## 六、质量与评测

### 6.1 三层质量门

| 层 | 检查 | 命令 | 阻断 |
| -- | ---- | ---- | ---- |
| 契约 | id / version / owner / 锚点符号 | `pnpm manifest:check` | ✅ |
| 产物 | `skills/` 与 manifest 零漂移、孤儿扫描 | `pnpm skills:check`（P3-T2 新增） | ✅ |
| 运行时 | 工具可见性、准入判定、审计留痕 | 契约套件 | ✅（observe 阶段不阻断调用，只阻断回归） |

### 6.2 Token 预算纪律（渐进披露）

- **索引层**：`id + 一句描述 + tags`，单条 ≤ 40 token，45 条合计 ≤ 1800 token
- **正文层**：仅在命中后加载，单技能 ≤ 800 token
- **参考层**：`references/` 仅在执行到指定 step 时按需读取

这是 Agent Skills 规范的核心价值，也是本仓「技能库」区别于「文档堆」的关键。

### 6.3 指标扩展（可选，需同步五维映射）

新增 3 项能力供给指标（与时/空/属/事/关联五维归属需补 `five-dimension-map.json`）：

| 指标 | 类型 | 语义 |
| ---- | ---- | ---- |
| `family_capability_skills_loaded_total` | Counter | 技能加载次数（按 id 维度可选） |
| `family_capability_mcp_tool_calls_total` | Counter | 工具调用次数（result 标签） |
| `family_capability_plugin_denied_total` | Counter | 准入拒绝次数（enforce 模式下） |

> 注意：指标总数将从 18 上升，需同步 README 口径与 4 条告警的基线。

| 风险 | 概率 | 影响 | 对冲 |
| ---- | ---- | ---- | ---- |

| 学习引擎沉淀的技能污染 manifest | 低 | 中 | `learned.*` 独立命名空间，晋级到 manifest 需人工审批（人工确认率已有指标可测） |
